Fix first

  1. H8: Billing can change payment-gateway keys.
  2. H7: Pharmacy can dispense the wrong drug with no warning.
  3. H6: The child dose check ignores the entered weight.
  4. M2: Every OPD visit is billed as an Emergency consultation (₹1,000).
  5. H1: The billing preview under-states pharmacy charges.

At a glance

Role security is strong. For every role, blocked pages redirected and admin-only server calls were refused, not just hidden in the menu.

Speed: pages load in 0.4–0.8 s. Running the server in Mumbai (bom1) instead of Washington DC (iad1) would make each data call about 5× faster.

Findings

  • H1

    Billing

    "Total pending" preview under-states pharmacy charges: Metformin shown as ₹3.00 and total ₹1,303, while the real invoice is 60 × ₹3 = ₹180, total ₹1,480.

    Reproduce
    Dispense 60 tabs → Billing → search patient.
    Fix
    Use qty × rate in the pending summary (same query as the invoice).
  • H2

    Doctor desk

    A completely empty consultation (no complaint, diagnosis, vitals or Rx) saves and marks the patient "Seen".

    Reproduce
    Open a token → Finish & next without typing.
    Fix
    Require at least a diagnosis or chief complaint.
  • H4

    Front desk (offline)

    When the save reaches the server but the reply is lost, the replay shows "Possible duplicate … same phone and name" instead of recognising its own request. Staff may register the patient twice.

    Reproduce
    Lose the network during "Register & issue token".
    Fix
    Have the server honour the idempotency key already sent by the client and return the original result.
  • H5

    Security / caching

    All /api/* responses (patient data) are sent with Cache-Control: public, max-age=0, must-revalidate. public allows shared or proxy caches to store patient data.

    Reproduce
    Check response headers.
    Fix
    Use private, no-store on authenticated API responses.
  • H6

    Doctor desk (patient safety)

    The child dose check keeps showing "! Child (8 y): record weight to check the Amoxicillin syrup dose" even after weight is entered (26 kg, typed by hand). The check ignores the weight on the form, so the mg/kg dose is never validated.

    Reproduce
    Child patient → enter Wt → prescribe Amoxicillin syrup.
    Fix
    Compute the check from the current form's weight, not the saved vitals.
  • H7

    Pharmacy (patient safety)

    The pharmacist can map a prescribed drug to any stock item with no warning (tested: Rx "Amlodipine 5mg" mapped to Ibuprofen 400mg, and "Mark dispensed" stayed enabled, no message). Wrong-drug dispensing isn't prevented.

    Reproduce
    Open an Rx → pick a different medicine in Stock item.
    Fix
    Auto-map by name/generic; require a reason or confirmation when the stock item doesn't match the prescribed drug.
  • H8

    Settings → Payments (security / finance)

    The Billing role can edit the hospital's payment gateway: Razorpay Key ID, Key Secret, Webhook Secret, Test/Live mode, Enabled. A billing staffer could enter their own Razorpay keys so patients' online payments go to their account. (Not saved during testing.)

    Reproduce
    Sign in as billing → Settings → Payments.
    Fix
    Make gateway configuration admin-only (server and UI); log and alert admin on any change.

What worked correctly

Duplicate service code, negative price, duplicate bed, expired batch, zero quantity, insufficient stock, discount over the bill, overpayment, double IPD admission, leave date range, invalid mobile and invalid GSTIN were all rejected with clear messages. Double-booking an appointment slot isn't possible. In Settings, Billing sees only the Payments tab (Users, Subscription and Services are hidden and refused). The audit log records every action with user and time.

Speed: why it's slow and how to fix it

Measurements

  • Every page is usable in 0.4–0.8 s (warm cache). The HTML arrives in about 90 ms and the JavaScript (~550 KB) is cached correctly for a year.
  • Each API call takes about 300 ms, but the server's own work is only 14–47 ms (Server-Timing: app;dur=17).
  • The response header shows x-vercel-id: bom1::iad1. Users hit the Mumbai edge, but the code runs in Washington DC (iad1), so every call crosses the world twice.
  • Each page makes 5–9 API calls. The dashboard calls /api/subscription/status 2× and /api/me/favourites 3×, and every page calls subscription/status and auth/me again.

Fixes, biggest gain first

#ChangeExpected gain
P1Move the Vercel functions to Mumbai (bom1) and keep the database in India (Supabase/Neon ap-south-1). In vercel.json, set "regions": ["bom1"].~300 ms to ~40–60 ms per call, about 5× faster everywhere
P2Load auth/me + subscription/status + favourites once per session (React context or SWR with a long cache), not on every page. Remove the duplicate calls.2–4 fewer calls per page
P3Combine each page's start-up calls into one endpoint (e.g. /api/frontdesk/bootstrap returns queue + doctors + fee).1 round trip instead of 5–7
P4Use stale-while-revalidate: show the last data at once (the front desk already caches fd.cache; do this on all pages) and refresh in the background.Pages feel instant
P5The patient dropdowns (Appointments, IPD admit) load all patients. Replace them with type-ahead search (/api/patients?q= already exists).Stays fast at 10,000+ patients
P6Poll /api/home/live only while the tab is visible, or use realtime push.Less server load
P7Split the JavaScript per role so Lab and Pharmacy users don't download Doctor desk, Billing and so on.Faster first load on slow hospital Wi-Fi
